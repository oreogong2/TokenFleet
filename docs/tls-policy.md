# Application certificate policy

At startup, before importing HTTP client modules, the application refreshes a private CA bundle from the Python build's original operating-system CA file and removes two distrusted root fingerprints. It sets SSL_CERT_FILE, SSL_CERT_DIR and REQUESTS_CA_BUNDLE; the CA directory remains empty. Certificate and hostname verification remain enabled. The fixed certifi version is pinned for clients that explicitly use its bundle.

The container's existing read-only filesystem and temporary writable directory are supported. Each process defaults to a new unpredictable, mode-0700 temporary directory. Deployment may set TOKENFLEET_TLS_SOURCE and TOKENFLEET_TLS_OUTPUT to explicit local paths; the output parent must already exist. Output must belong to the effective user, with no group/other write access. Ancestors must belong to that user or root and deny other writers, except root-owned sticky temporary directories. Root must not reuse another user's output. Invalid or unavailable input stops application startup. No platform trust store is modified.

This POSIX helper requires fcntl and directory file descriptors. The manifest detects accidental inconsistency; it does not authenticate files against an attacker with the same operating-system identity. Keep the output for the entire process lifetime, including later TLS requests. Container tmpfs is cleared when the container is replaced; on other hosts, use a protected persistent output directory if temporary-file cleanup could remove a running process's bundle.

The normal application startup path applies this policy after fresh builds and restarts. Standalone maintenance commands that do not import the application must use their own verified CA settings. Rollback uses the previous application image and retains its prior certificate behavior.
